# Техническая передача

## Копии: текущее состояние и недостающие настройки

03.10.2026 в авторизованной панели Amvera подтверждены две встроенные копии `/data`: 02.10 03:43:54 и 01.10 11:50:50. [Документация Amvera](https://docs.amvera.ru/applications/backups.html) описывает хранение за последние два дня. Это не подтверждает отдельный экспорт PostgreSQL и не выполняет требование семи полных ежедневных копий.

Для запуска нужны: защищённое хранилище достаточного объёма вне эфемерного контейнера (предпочтительно вне приложения), доступ к нему из задания; PostgreSQL client `pg_dump` совместимой версии; секреты подключения к БД; ежедневный планировщик; уведомление о неудаче задания и ответственный за восстановление. Платные хранилища и задания не создавались. `BACKUP_ROOT` в серверной конфигурации отсутствует. Семь копий пока не накоплены.

Готовая команда создаёт согласованный дамп БД, архив пользовательских media с оригиналами, JSON-манифест с SHA-256 и проверяет его. Старые копии удаляются только после успешного создания новой; хранится минимум семь завершённых наборов. Незавершённые `.pending-bs-*` не считаются копиями, проверяются администратором отдельно. Отказ не скрывается успешным статусом. Не размещайте копии внутри MEDIA_ROOT и не делайте хранилище публичным.

```sh
python manage.py backup_site --root /protected-backups/best-season --keep 7
python manage.py backup_site --verify /protected-backups/best-season/bs-TIMESTAMP
```

Пример ежедневного задания Linux, **после настройки хранилища и окружения**, не установлен автоматически:

```cron
15 3 * * * /path/to/venv/bin/python /path/to/BS/manage.py backup_site --root /protected-backups/best-season --keep 7
```

Планировщик должен получать production-настройки и секреты безопасно, без токенов в команде или журнале. Для S3 требуется отдельный защищённый этап загрузки с проверкой и политикой хранения; текущая команда пишет в каталог, а не в S3. На время полного снимка исключите удаление/замену медиа редакторами, иначе дамп и файловый архив могут относиться к разным состояниям. Публичное чтение страниц может продолжаться.

## Восстановление: только отдельная среда

1. Создайте отдельное приложение/окружение, отдельную пустую БД и отдельный каталог media. Проверьте абсолютные пути и имя БД; они не должны совпадать с production. Отключите Telegram/email и внешние платежи в тестовой среде.
2. Возьмите завершённый набор и проверьте `backup_site --verify`. Сверьте дату и хеши; исходную копию сохраните.
3. Для PostgreSQL восстановите в **пустую отдельную БД**: `pg_restore --no-owner --no-acl --dbname=bs_restore /path/to/copy/database.dump`. Подключение передавайте окружением/защищённым password file. Не применяйте `--clean` к production. Для SQLite скопируйте `database.dump` в новый файл БД и укажите его в настройках тестовой среды.
4. Распакуйте `media.tar.gz` только в новый каталог media после проверки архива. В архиве разрешены обычные файлы, без абсолютных путей, выхода через `..` и символьных ссылок.
5. Используйте код соответствующей копии, затем выполните `migrate`, `check`, `collectstatic --noinput --ignore=*originals*`, `prepare_site_images --strict`.
6. Проверьте число страниц и фото, вход в админку, оригиналы и галереи, тексты документов, черновики, заявки и UTM без вывода персональных данных. Восстановление не должно само отправлять уведомления.
7. Зафиксируйте дату, исполнителя, контрольные результаты и длительность. Переключение production — отдельная операция с разрешением владельца.

Автотест создаёт восемь копий изолированной SQLite и медиа, проверяет остаток из семи, восстановленные значения и выявление повреждения. Дополнительно создана копия текущей локальной БД и media: в отдельном каталоге восстановлены 91 таблица и 9821 файл, количества строк и SHA-256 файлов совпали. Это **не** подтверждает восстановление рабочей PostgreSQL или серверных `/data`.

## Уведомления и аналитика

В панели приложения 03.10 проверены только имена переменных, без вывода значений. Присутствуют DB-настройки; Telegram, SMTP, NOTIFY_EMAIL и BACKUP_ROOT отсутствуют. Настройку доставки должен завершить владелец каналов. Реальные заявки и сообщения в рамках работы не отправляются.

Проверка целей после получения доступа:

1. В настройках сайта подтвердите существующий ID счётчика; в Метрике откройте цели этого счётчика, не создавайте новый аккаунт.
2. В чистом профиле до согласия на Cookies не должно быть запроса `mc.yandex.ru/metrika/tag.js`. После согласия проверьте его загрузку. Отказ не включает счётчик.
3. Откройте существующие входы в бронирование: шапка, главный экран, блок «О нас» главной, карточки домов, дом и мобильная липкая кнопка. Проверьте `booking_widget_open` и параметр `entry_point`; при ошибке SDK — `booking_widget_error`. Удалённая нижняя кнопка дома не возвращена.
4. Проверьте `contact_click` с `channel=telegram`, `whatsapp` или `phone`, `directions_view`, `directions_click` (кнопка маршрута) и `house_scroll_75`. Последнее событие отправляется один раз после просмотра **более** 75% страницы дома.
5. По отдельному разрешению отправьте тестовую заявку без данных гостя. Только после сохранения и ответа сервера должно появиться `form_submitted`, а для резервной формы — также `booking_fallback_submitted`. Ошибочная валидация и URL с `?form=ok` без серверного подтверждения не должны давать цель.
6. Через 15 минут проверьте отчёт по целям, источник и параметры. Сопоставьте сохранённую заявку с Telegram/email и пятью UTM. До этого результат считается подтверждённым только тестами.

На 03.10 браузер не авторизован в Метрике; отчёты и настройки целей не проверены. Вебмастер также требует входа. Ни одно событие в этой задаче не подтверждено настоящим отчётом Метрики. Контроль JS выполнен тестами с подменой счётчика и SDK.

Внешние публичные соцсети/агрегаторы получают `utm_source=best_season`, `utm_medium=referral`, `utm_campaign=outbound`, `utm_content` по месту ссылки. Служебные SDK, неизвестные хосты и платёжные ссылки не преобразуются. Canonical и sitemap используют настроенный Wagtail Site: основной домен в рамках этой задачи не меняется.

## Ограничения при приёмке

Точки каруселей сохраняют согласованный шаг: неперекрывающиеся зоны 44×44 при нём невозможны. Ограничение оставлено по решению пользователя. У дней календаря на узких экранах шаг также меньше 44 px: зона ограничена шириной ячейки и не перекрывает соседнюю дату; увеличение потребовало бы изменения согласованных размеров календаря. В плотных ссылках футера и соцсетей правило 44×44 также ограничено текущими расстояниями. Шрифты, оттенки, изображения, композиция и правила бронирования не меняются. Физические iOS/Android, Safari, Firefox и Яндекс Браузер нельзя считать проверенными по эмуляции ширины в доступном встроенном Chromium.

Дополнительные юридические тексты, отсутствующие среди пяти оригиналов, не сочиняются. Низкое разрешение исходников нельзя исправить без новых оригиналов. Правила и тарифы в Контуре, настоящая оплата и окончательное бронирование требуют отдельной проверки у поставщика.
